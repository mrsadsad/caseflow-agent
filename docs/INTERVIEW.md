# 把 CaseFlow 讲成你能独立负责的项目

这份项目可以证明你对 Agent 应用的执行边界、持久化与评测有工程理解，但不能保证获得大厂录用。准备投递时，最有说服力的是能独立运行、修改和解释的证据，而不是再增加一个项目名称。

## 三分钟介绍

可以用自己的话讲清下面四段，避免逐字背诵。

> 我做的是售后处理 Agent：接到退款诉求后，查询当前客户的订单，检索适用政策，决定补问、转人工、回答或提出退款方案。模型只能提出方案；实际执行需要人工批准，并经过确定性的业务规则校验。
>
> 难点是模型决定的不确定性与业务执行的确定性需要分开。案例固定租户和客户，检索先按租户及当前版本过滤；提案记录金额、订单版本与政策依据。批准时重新检查快照，防止用户批准的是旧方案。
>
> 我把批准结果和执行任务放在同一个数据库事务里，再由投递器执行。重点演示是：退款台账已写入后进程崩溃，Outbox 还没有确认；恢复后重投同一个幂等键，只得到同一笔退款记录。这里验证的是本地模拟器，不是实际支付系统。
>
> 我用固定脚本验证工程机制，并把真实模型表现单独记录。评测关注合法方案、无效动作拦截、重复执行、版本变化、成本与失败原因。项目还有明确边界：单机数据库、本地服务、人工构造案例，没有生产业务量或线上收益证据。

“我设计”“我实现”只用于你实际亲自负责并能独立解释的部分。AI 协助生成的代码应如实说明；使用工具并不妨碍展示能力，无法解释运行机制才会让面试证据失效。

## 五分钟演示顺序

1. 按 README 启动工作台，先明确当前是固定演示还是真实模型。
2. 打开一个可退款案例，查看工具事件、检索来源与退款提案，解释为何此时台账还没有退款。
3. 展示金额和版本，再批准该提案，指出待投递任务已经持久化。
4. 使用工作台的崩溃演练，让模拟台账写入成功但投递确认失败；查看台账与待处理任务的不一致状态。
5. 再次投递，展示台账仍只有一笔且任务最终完成，解释重复投递与重复退款的区别。
6. 展示一项越权、过期或信息不足案例与对应测试，最后说明尚未验证的真实模型与生产边界。

演练会改变本地案例状态；需要从头展示时，按 README 指定独立的演示数据库，不要直接删除含有其他实验记录的数据库。完整终端输出和失败记录比剪辑后的成功截图更容易复核。

## 面试追问与回答要点

| 问题 | 应当讲清的因果关系 |
| --- | --- |
| 为什么需要 Agent，固定流程能不能做？ | 订单校验与执行本来就适合固定流程。Agent 的价值假设在于理解不同诉求、选择查询和补问信息；需通过对照验证，不因用了 LLM 就认定更好。 |
| 为什么不让模型直接调用退款？ | 模型输出可能错误、受不可信文本影响或引用旧数据。权限与金额必须由代码验证，用户批准具体方案后才产生执行任务。 |
| 为什么检索前做租户过滤？ | 先全量检索后让模型自行忽略会暴露他人数据，也可能让无权内容影响答案。范围由服务端身份上下文确定，不能相信模型提供的 tenant_id。 |
| 引用了政策 ID 就能证明回答正确吗？ | 只能证明来源存在且满足可访问条件，不能证明语义支持。需要业务规则、答案评测和人工抽查各自负责不同层面。 |
| 批准之前为什么还要查版本？ | 调查与批准之间订单或政策可能变化。批准旧快照会产生 time-of-check/time-of-use 问题，应重新校验并拒绝过时方案。 |
| Outbox 解决了什么，没解决什么？ | 它把业务批准和待投递消息原子落库，避免任务丢失；无法单独保证外部副作用只发生一次，仍需接收端幂等及状态查询。 |
| unique 幂等键是否足够？ | 同一任务的重投可以去重，但两个不同提案可能有不同键。还需要订单级的状态或可退额度约束。 |
| 退款成功但进程不知道怎么办？ | 保留未知状态，查询相同幂等键的结果；不可自动换新键再次退款。演示利用唯一台账记录重放，真实网关需要查询及对账协议。 |
| CAS 与幂等有什么区别？ | CAS 防止并发旧状态覆盖新状态；幂等防止同一业务动作重复产生效果。两者保护不同不变量，不能互相替代。 |
| 崩溃后继续 Agent 会不会多花钱？ | 请求前预留步数，恢复沿用原预算；结果未知的模型调用仍可能已计费，应标记用量不完整，不能当成免费请求。 |
| 为什么没有多 Agent 或向量数据库？ | 当前主要风险是授权和执行一致性。多 Agent、向量检索需要在特定数据和任务上证明收益，再接受额外复杂度与成本。 |
| 怎么扩展为生产服务？ | 先补身份认证、持久任务领取与租约、真实网关适配和对账、权限及审计要求，再基于测量决定数据库与队列方案。当前版本不能直接宣称支持这些能力。 |

## 你必须亲自完成的练习

1. 不依赖生成工具，沿着一次批准操作追踪 `server → store → outbox → ledger`，指出每个事务何时开始与结束。
2. 写出“已退款、未确认”的两个持久化事实，解释为什么直接将失败任务标成未执行会出错。
3. 增加一个业务案例，例如存在部分已退金额的订单；先明确预期与边界，再修改规则和有意义的测试。
4. 构造两个不同提案争用同一订单的场景，证明系统不仅能抵抗同一消息重投，也能处理不同请求的业务冲突。
5. 分析一次真实模型失败，区分理解错误、检索失败、工具参数错误、业务规则拒绝与基础设施失败。保留原始运行记录。
6. 在冻结案例上比较改动前后，报告所有尝试、实际分母、成功标准、调用量、token 和耗时。无提升也应保留。

这些练习没有完成之前，不要把相应能力写成已经独立掌握。项目之外仍需准备 Python、SQL、HTTP、事务、并发与常见数据结构，能够现场实现和调试。

## 简历描述模板

按真实完成的贡献替换括号内容：

> 在 AI 协助下构建售后处理 Agent 工程原型，个人负责（实际负责部分）；实现受范围约束的工具调用、政策来源追溯、带版本校验的人工审批，以及 Outbox 与幂等退款模拟器；通过（实际测试或实验）验证（实际结果），分析（失败类型与代价）。

真实模型实验完成后，才可以增加样本量、成功率和成本数字，并注明人工构造案例、模型版本与预算。不要将固定脚本准确率写成模型成功率，不要把本地模拟退款写成支付业务落地，也不要写未经测量的“效率提升 80%”。

| 了解模型能力的边界 | 固定演示与真实调用分开记录，保留无效工具选择和成本 |
| 有评测意识 | 冻结案例、预先定义的成功标准、所有尝试及数据限制 |

这些是作品集的工程证据建议，不是任何公司的官方录用条件。岗位要求和个人经历不同，投递时需要按实际岗位重新核对。
