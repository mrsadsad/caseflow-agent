01 / ORCHESTRATION

模型负责建议，工具负责约束

Live 模式以真实模型产生工具调用；服务端逐个验证调用并持久化结果。订单归属、可退金额、有效政策和审批状态始终由业务代码验证。

请求与案例作用域模型 / Demo 策略受控工具调用状态与事件落盘

Demo 用固定策略复现流程，不能用来证明模型理解能力。评估真实模型时，应单独运行 Live 评测并检查失败样本。

02 / SECURITY

不把检索内容当作权限

租户与客户身份来自存储的案例，模型不能自选。政策检索先按租户与当前版本过滤，再做文本排序；政策来源与版本进入审批提案。

审批前再次核对金额、订单版本与政策版本。模型没有“批准”和“转账”工具。浏览器只访问本机服务；API Key 始终留在服务端环境中。

03 / RELIABILITY

恢复执行也必须遵守原预算

执行步骤和消息存入 SQLite。请求前保存预算预留；网络结果不确定时，费用统计会标记为不完整，避免伪造精确成本。

恢复任务沿用原步骤预算。已耗尽预算的任务不能通过“恢复”绕过限制。运行队列最多容纳 8 个活动任务，2 个工作线程并发执行。

04 / SCOPE

可演示的工程原型，有明确边界

这是单进程、本机运行的 Agent 应用项目。退款服务使用 SQLite 模拟器；外部支付系统还需要对方支持幂等键及可查询的执行状态。

检索使用轻量文本排序，未接入向量数据库。没有企业登录、分布式任务调度或生产监控平台；设计说明与面试材料会继续解释这些扩展点。
